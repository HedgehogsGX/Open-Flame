# 上传器外部验收测试计划

本计划供受委托的测试员在自己的 Windows 测试环境执行，首批范围精确为 **Bilibili、抖音、视频号**。其他平台后续处理。每个平台分别判定，不能用一个平台的成功代替其余平台。

执行前阅读 [上传指南](UPLOADER.md) 与 [上传运行环境](UPLOAD_RUNTIME.md)。本文是测试步骤，不是登录、上传或发布授权：真实扫码、手机确认、媒体选择和最终投稿均由测试员本人决定并操作。只使用自己管理的测试账号，以及自己创作或已获准用于相应平台投稿的测试媒体。

## 快速开始：先检查本地控件

**获取本次测试源码：** 使用 `codex/uploader-first-platforms` 分支。任选一种方式取得完整源码：

- **浏览器下载：** 打开 [GitHub 测试分支](https://github.com/HedgehogsGX/Open-Flame/tree/codex/uploader-first-platforms)，选择 `Code → Download ZIP`，或使用 [测试分支源码 ZIP](https://github.com/HedgehogsGX/Open-Flame/archive/refs/heads/codex/uploader-first-platforms.zip)。解压完整目录，在含 `Setup-Open-Flame.cmd` 的源码根目录继续。
- **Git 克隆：** 在准备存放测试源码的位置执行下列命令；`Open-Flame-upload-test` 应是尚不存在的新目录。

```powershell
git clone -b codex/uploader-first-platforms --single-branch https://github.com/HedgehogsGX/Open-Flame.git Open-Flame-upload-test
Set-Location .\Open-Flame-upload-test
```

本次交付入口是测试分支源码；获取后仍需完成以下安装与构建身份核对。不要沿用此前本地测试 ZIP 的构建身份，本轮交互修复改变了源码构建散列。

1. **启动并记录构建。** 按第 2 节完成安装，打开 `/uploads`，点击“刷新状态”，执行该节命令记录版本、构建身份和运行环境结果。
2. **检查两种导入入口。** 本地短片：选择文件后点击“导入视频”。下载成品：点击“用于上传”打开上传页，再点击“导入此下载成品”。核对文件名、大小和 SHA-256；这一步不向平台传视频。
3. **检查本地草稿。** 如已有测试账号，选择账号并填写信息，点击“创建本地草稿并预览”。核对“查看投稿信息”，确认任务保持“本地草稿”；可测试“取消”和“重新创建本地草稿”。没有账号时先完成导入与刷新检查，草稿用例在本人决定登录后补做。
4. **检查详情刷新。** 折叠一份任务的“查看投稿信息”，保持另一份展开；等待至少 10 秒，再点击“刷新状态”。各任务的展开/折叠选择应保持，具体见 `DRAFT-05`。
5. **再决定是否进行真实平台测试。** 愿意登录时，按第 4 节逐平台点击“添加并扫码登录”并自行扫码；愿意投稿时，再执行第 5 节，每份草稿只点击一次对应的最终确认按钮。视频号“确认上传并保存平台草稿”也会真实传输视频；“确认立即上传投稿”会尝试投稿。未授权的项目记为 `NOT RUN`。
6. **回报结果。** 按第 7 节模板填写通过、失败或受阻的用例；出现 `unknown` 先执行第 6 节的远端核对，不直接重发。截图遮挡二维码及账号资料。

首次可以只完成上述本地检查并回报；真实登录、平台草稿和投稿分别记录，当前已有证据的边界见下表。

## 2. 首次安装与版本记录

1. 准备 Windows x64、可写本地目录和测试所需磁盘空间。普通源码版按 [Windows 首次安装](WINDOWS_SETUP.md) 完成 Setup，再按 [启动指南](WINDOWS_LAUNCHER.md) 使用 Start。源码版仍需已有 Python，不是免 Python EXE。
2. 按 [上传运行环境的安装章节](UPLOAD_RUNTIME.md#安装) 安装可选运行时。上传运行时需要已有 **CPython 3.12 x64** 来创建独立 venv；主应用可使用其自身支持的 Python。严格使用该文档中与源码安装或包安装对应的命令；源码用户需保留其临时 `PYTHONPATH` 步骤。
3. 上传运行时的 `--root` 必须对应本次应用的数据目录。普通 Start 默认是 `%LOCALAPPDATA%\Open-Flame\video-download-control\data-uploads`；使用自定义应用根时，按上传指南确定对应位置。不要把另一实例的运行时就绪当作本实例就绪。
4. 安装后执行运行环境文档中的 `--check`，打开本次应用的 `/uploads` 并刷新状态。记录结果；缺失或校验失败时先处理安装问题，不进入真实投稿测试。检查页面本身不会自动安装组件。
5. 在**当前运行应用**上读取版本与构建身份。以下 PowerShell 只读取本地接口；如果启动使用其他端口，先修改 `$uploadTestBase`。只保存下面筛选后的输出，不提交完整 API 响应。

```powershell
$uploadTestBase = 'http://127.0.0.1:8000'
$uploadTestIdentity = (Invoke-RestMethod -Uri "$uploadTestBase/api/v1/capability-snapshot?limit=1").current_product_identity
$uploadTestStatus = Invoke-RestMethod -Uri "$uploadTestBase/api/v1/uploads/status"
[pscustomobject]@{
    version = ($uploadTestIdentity -split '\+build\.sha256\.')[0]
    product_identity = $uploadTestIdentity
    upload_runtime_ready = $uploadTestStatus.backend.ready
    upload_runtime_code = $uploadTestStatus.backend.code
}
$uploadTestStatus.platforms | Select-Object id, name, title_limit, modes
```

若身份读取报 `product_build_drift` 或身份不可用，记录错误并正常停止、重新启动同一份交付构建后重查。测试过程中不要修改或覆盖应用源码。本文不固定某个旧版本或 hash；每次测试、换包或重启到新构建后重新记录。

## 3. 测试材料与执行规则

- 为每个测试准备可辨认的短片，例如带测试编号的自制 MP4；保持文件小、音画清晰，并记录文件名、大小、SHA-256、时长和编码。平台实际编码、尺寸、时长与账号限制由平台决定；应用接受扩展名不代表平台必然接受。
- 准备两条入口：`L` 为本地文件导入，`D` 为下载成品列表中已完成原件的“用于上传”；点击后仅打开上传页，还需点击“导入此下载成品”，才会复制并登记原件。`D` 使用可合法下载且允许再次投稿的自有或授权视频。下载成功不会自动取得转载许可，也不会自动授权上传。
- 三个平台各完成 `L`、`D` 两个入口到**本地草稿**的检查。真实投稿阶段每个平台先做一个最小案例，并在总体测试中覆盖两种入口；需要比较同平台两入口时另建不同测试编号，经本人确认后再执行。
- Bilibili 必须选择真实分区、至少一个标签，并明确原创或转载；转载填写真实来源。不要因为文件是下载成品或文件已导入，就默认其属于原创。
- 每份本地草稿在最终确认前逐项检查：测试编号、视频、平台、账号备注、标题、简介、标签、投稿类型/来源、分区和动作。首次真实验收每次只确认一个任务。
- 结果使用 `PASS`、`FAIL`、`BLOCKED`、`NOT RUN`。`PASS` 只表示该行预期已观察到；平台审核中应单独写“平台已接收，审核中”，不能写成已公开。

## 4. 本地与登录矩阵

本节不要求上传视频。登录相关请求会访问平台；测试员只在愿意授权本次登录时扫码并确认。

| ID | 平台/入口 | 操作 | 预期与记录 |
| --- | --- | --- | --- |
| ENV-01 | 全部 | 按第 2 节安装、`--check`、打开 `/uploads` | 页面可用，运行环境就绪；记录当前版本、构建身份与固定错误码。安装/help 检查不应触发扫码或投稿。 |
| AUTH-01 | 三平台分别 | 选择平台，备注留空或填写测试备注，点击“添加并扫码登录” | 本页显示对应账号和二维码；登录不打开终端或独立外部登录窗口。记录取码耗时，截图前遮挡整个二维码。 |
| AUTH-02 | 三平台分别 | 使用 Bilibili App、抖音 App、微信分别扫码；按手机提示自行确认 | 面板应区分等待扫码、等待确认与终态。二维码在离开等待扫码状态后隐藏；只有认证完成才显示登录成功。Bilibili 手机授权页可能显示 TV 客户端。 |
| AUTH-03 | 三平台分别 | 登录成功后点击“检查登录态”，再刷新页面 | 账号应为 `ready/account_ready`；记录检查结果。此结果仍不代表账号所有投稿权限已验证。 |
| AUTH-04 | 三平台分别 | 重新扫码登录，在二维码出现后点击“取消登录” | 旧二维码立即隐藏，操作结束，不应稍后被旧回调恢复为成功。原登录文件不应被未完成扫码的结果替换；不要读取其内容，通过“检查登录态”确认旧会话是否仍有效，平台撤销等原因另行记录。 |
| AUTH-05 | 三平台分别 | 开始登录但不扫码，观察过期/有界超时；需要继续时点击“重新获取二维码” | 旧码不可继续显示；自动换码或手动重新获取应对应新的登录二维码，不重新添加重复账号。记录实际等待时间和终态；不要把未知 TTL 填成平台确定的有效期。 |
| AUTH-06 | 遇到时执行 | 记录短信、滑块、身份验证、账号无权限等提示 | 应明确提示额外验证或失败，不能显示假成功。仅在手机/平台明确提供的正常流程中由本人处理；当前页无法完成时取消并标 `BLOCKED`，不提供验证码给维护者。 |
| AUTH-07 | 三平台分别 | 无上传任务运行时，正常停止并重启应用；回到账号列表并检查登录态 | 已保存账号仍可检查；未完成的登录不会自动继续。需要重登时明确提示，不应偷偷使用其他账号。 |
| SRC-01 | 三平台 × `L` | “选择本地视频”→“导入视频”→选择导入项 | 正确显示文件名、大小、SHA-256；未开始平台上传。每个平台用该来源创建一份本地草稿。 |
| SRC-02 | 三平台 × `D` | 下载首页打开已完成成品，点击原件的“用于上传”；上传页打开后，再点击“导入此下载成品” | 点击“用于上传”仅打开页面；点击“导入此下载成品”后才复制并登记正确原件，显示的大小和 SHA-256 与成品一致。每个平台用该来源创建一份本地草稿，不应自动投稿。 |
| SRC-03 | 本地 | 用专门测试文件尝试空文件、不支持扩展名；大于 2 GiB 案例仅在已有测试材料时执行 | 给出明确错误，不产生可投稿来源。不为测上限占满磁盘，不修改或损坏正常下载成品。 |
| SRC-04 | 本地视频选择控件 | 导入至少两份测试视频，先选择其中一份，再把“已导入的视频”改为“请选择视频”。等待至少 10 秒并点击“刷新状态”，再次等待自动轮询。 | 始终保持无选择，SHA-256 信息清空，不自动重选首项或其他视频。其他必填项已填时，点击“创建本地草稿并预览”应要求先选择视频，不创建任务；重新手动选择视频后信息正常恢复。 |
| DRAFT-01 | 三平台 × `L/D` | 填写信息，点击“创建本地草稿并预览”，等待至少 30 秒并刷新页面 | 任务保持 `draft`；账号、来源和字段对应正确。该动作只写本地记录，不传视频、不投稿。平台后台不应出现该测试编号的新内容。 |
| DRAFT-02 | 三平台 | 尝试空标题、超过页面显示的标题限制；Bilibili 另测缺分区、缺标签、未选原创/转载、转载缺来源 | 页面或服务明确阻止，不创建可执行任务。当前标题上限 Bilibili 80、抖音 30、视频号 100；以本次构建状态接口及页面提示核对。 |
| DRAFT-03 | 多账号本地检查 | 勾选多个测试账号创建草稿；仅查看每项预览，不确认执行 | 每个账号有独立草稿，内容和平台映射正确；不会因勾选多个账号自动发送。最多 20 个账号，首轮无需为测上限新建大量账号。 |
| DRAFT-04 | 全部 | 取消一份尚为 `draft` 的任务 | 变为 `canceled`，平台无新增；“重新创建本地草稿”只产生待确认草稿，不自动执行。 |
| DRAFT-05 | 本地详情控件 | 准备两份本地任务，把一份“查看投稿信息”折叠、另一份展开；等待至少 10 秒，再点击页面内“刷新状态”。交换两份的展开/折叠状态并重复；再创建一份新草稿。 | 自动轮询和“刷新状态”后，各任务保留各自的展开/折叠选择，已有选择不受新任务影响；新草稿默认展开。此用例不点击最终投稿确认，也不要求浏览器 F5 重新加载后保存折叠状态。 |
| DRAFT-06 | 本地重建提示 | 创建草稿 A 并“取消”；从 A 点击“重新创建本地草稿”得到后继 B，再取消 B。回到旧 A，再次点击“重新创建本地草稿”。全程不点击最终投稿确认。 | 再次操作旧 A 应返回其已有后继 B，任务总数不增加，并准确提示已有后继的当前状态（本例为 B 已取消）；不能误报“新本地草稿已创建”或暗示 B 仍待确认。记录操作前后任务数量和提示。 |

## 5. 测试员逐项授权的真实投稿

执行每行前由测试员确认该账号、媒体和远端动作。账号可用但不愿发布时，停在本地草稿并把投稿行记为 `NOT RUN`。不要为了得到绿色状态反复点击确认。

**本地草稿与视频号平台草稿是两件事：** `draft` 位于 Open-Flame 本地，尚未授权传输；选择视频号“上传并保存平台草稿”并最终确认后，会真实传输视频并在视频号后台保存，预期本地结果为 `draft_saved`。选择“立即上传发布”并确认则会尝试投稿，预期本地结果为 `submitted`。两者都必须去视频号后台核对，后者仍可能处于审核中。

| ID | 平台 | 执行步骤 | 平台核对与验收 |
| --- | --- | --- | --- |
| LIVE-B1 | Bilibili | 使用已 `ready` 的测试账号；选择 `L` 或 `D` 来源，填写有效分区、标签、原创/转载及来源。创建并核对草稿后，由本人点击一次“确认立即上传投稿”。 | 记录 `queued → running → 终态`、耗时和安全错误码。到 Bilibili 创作中心按测试编号核对是否接收、账号、音画、标题、简介、标签、分区和转载来源；分别记录稿件标识、审核状态、公开状态。 |
| LIVE-D1 | 抖音 | 先完成真实扫码及登录态检查；选择另一入口以补齐 `L/D` 覆盖，创建并核对草稿后，由本人点击一次“确认立即上传投稿”。 | 到抖音创作者中心核对是否接收、账号、音画、标题/正文和标签。文字被截断、合并或平台修改时记实际差异；分别记录接收、审核与公开状态。 |
| LIVE-T1 | 视频号平台草稿 | 仅选择视频号账号，在“确认后的动作”中选“上传并保存平台草稿”。预览仍应为本地 `draft`；本人确认后开始真实上传。 | 本地若为 `draft_saved`，在视频号助手核对草稿列表、目标账号、视频和文案；确认没有因此变成已发布作品。找不到远端草稿时记录为待核实或失败，不能仅凭本地状态判成功。 |
| LIVE-T2 | 视频号投稿 | 新建不同测试编号的本地草稿，明确选择“立即上传发布”，核对后本人点击一次“确认立即上传投稿”。此行不会自动把 LIVE-T1 的远端草稿转换为发布。 | 在视频号助手核对作品是否接收、内容与账号；分别记录审核、可见性和公开结果。不要手动发布 LIVE-T1 草稿后又误以为本行工具已成功。 |
| LIVE-E1 | 覆盖补充 | 完成前三平台至少一例真实投稿后，检查真实测试是否同时覆盖 `L` 和 `D`；缺少哪种入口，再授权一例对应测试。 | 回报明确列出“平台 × 入口 × 模式”，不要把仅成功导入的入口记为真实上传成功。无需默认重复六次投稿。 |

`submitted` 只表示上游工具报告提交完成；`draft_saved` 只表示上游报告草稿保存完成。远端不存在、内容不一致或重复出现都应单独回报。平台审核拒绝与本地技术失败分开记录；平台要求的修改由测试员自行决定。

测试产生的远端内容由测试员按自己的保留决定在平台处理。Open-Flame 的取消不是撤稿或删除功能；本计划不要求自动删除任何已接收内容。

## 6. 取消、中断与 `unknown`

这组测试可能在平台留下内容，需使用已授权的专用测试媒体。先完成至少一个正常流程再执行；不要通过强杀所有 Chrome、删除账号文件或改数据库制造故障。

| ID | 操作 | 预期与核对 |
| --- | --- | --- |
| REC-01 | 当任务仍为 `queued` 时点击取消；如已变 `running`，按 REC-02 记录 | 未开始的任务应为 `canceled`，不得随后自动执行。平台应无新增；状态竞态要记录点击时与最终状态。 |
| REC-02 | 对本人已授权的测试投稿，在 `running` 时请求取消 | 操作有界停止；已经开始后的结果可能为 `unknown`。取消不能证明平台没有收到，也不能撤回已提交内容。必须查远端草稿、作品与审核列表。 |
| REC-03 | 对本人已授权的测试任务，在 `running` 时正常停止应用，再用同一数据目录启动 | 中断结果应保留或恢复为 `unknown`，不能自动重新上传。记录重启前后状态，并核对平台是否已有内容。 |
| REC-04 | 有尚未开始的 `queued` 任务时正常重启应用；没有稳定排队窗口则标 `NOT RUN` | 原排队任务退回需再次确认的本地 `draft`，不能开机后自动补发；原本地草稿应继续保留。 |
| REC-05 | 如出现 `unknown`，先不勾选核对框，尝试“重新创建本地草稿” | 应要求先核对平台结果。若平台仍在处理或暂时查不到且不能确定是否接收，保持 `unknown`，不要勾选后重发。 |
| REC-06 | 确认远端结果后，由测试员决定是否确需重试；如需要，勾选核对框并重新创建草稿 | 原任务保留，新任务为待确认 `draft`；仍需再次核对和最终确认。若远端已收到原稿且无需重试，则不创建重复投稿。 |

发生 `unknown` 时按以下顺序回报：记录任务编号/时间/模式 → 用正确账号查平台草稿、作品及审核列表 → 记录找到、仍处理中或未能确认 → 决定等待或是否确需新草稿。网络错误、取消和超时本身都不能作为“肯定没上传”的证据。
