# Iteration 0.28.0 whole-workflow cancellation evidence

Validated: 2026-09-09. Source baseline: `548d5efb0e0c1f2691182d97be284c0e982240de`; current working-tree evidence, not a frozen release receipt.

## Result

`POST /api/v1/workflows/{id}/cancel` now stores a revision-fenced `workflow_cancellation_requested` intent before touching a domain operation. The background reconciler includes this intent after restart and repeatedly addresses the furthest workflow-owned operation: upload jobs, render plan, AI project, or download batch. If a domain object was created before its workflow reference checkpoint, cancellation discovers it by the workflow's stable request identity. Download discovery remains read-only. Editing and Upload write a request tombstone in the same domain transaction when the stable request is absent, so a creator waiting behind that transaction cannot publish a replacement after cancellation. Only a confirmed `stopped` result becomes `canceled/workflow_canceled`.

The supported application keeps one supervisor per app root. Within that process, every `WorkflowService` for the same normalized database path shares one re-entrant mutation lock. Workflow reference and state writes also compare the record's previously read revision, state, and code in their SQLite transaction. A stale advance therefore cannot overwrite a committed cancellation intent, and explicit confirm/retry requests are rejected after cancellation starts.

Each domain remains the authority for its own stop semantics:

- Download cancellation verifies the batch name, original source URL, input set, and current durable state before using the existing Worker control path. Missing checkpoints after either a process crash or a handled domain exception recover through the same discovery-only path; no match is stopped, one exact match is canceled, and ambiguity or mismatch requires attention.
- AI and render cancellation validate the complete retry graph without an arbitrary lineage-depth limit. Cycles, missing or multiple successors, and operation/source/request identity drift fail closed. AI project graph enumeration, current-leaf selection, successor fencing, remote-invocation ledger checks, tombstone creation, and every leaf state change occur in one Editing `BEGIN IMMEDIATE` transaction. Unknown or reconciled remote evidence is preserved with its exact durable code for review.
- Upload cancellation validates the full v2 stable-request digest, including source, account set, every per-account target, title, description, tags, category, mode, schedule, cover, and every platform option. It separately validates stored root order, then checks one to thirty exact `job/source/account/platform` slots and their frozen account/platform bindings in one Upload `BEGIN IMMEDIATE` transaction. Retry-leaf discovery uses explicit cycle detection rather than an arbitrary lineage-depth limit. A login revision change does not prevent emergency stop of an otherwise identical immutable job. Draft/queued rows become canceled together; running rows persist a cancellation request before the backend stop event is set. A missing stable request becomes a v2 empty-job tombstone that survives Upload backup and restore and continues to fence `create_jobs`.
- Running or canceling work remains waiting. Unknown domain results, identity mismatch, incomplete graphs, and partially completed platform fan-out become explicit attention. Only a fully checkpointed upload fan-out whose every leaf is already `submitted` or `draft_saved` records its original submission/draft/mixed outcome; a successful leaf in a pending, uncheckpointed slot becomes `upload_partially_completed` for manual review.

The production workflow page sends the current revision and CSRF token, hides confirm/retry/advance actions while cancellation is pending, offers a deterministic recheck action, rejects stale in-flight poll responses, and restores the corresponding control or card focus after polling redraw. The editing page hides cancellation actions that durable ledger evidence will reject while retaining the safe stop action for an active owner, and it presents retry-lineage conflicts as user-facing refresh guidance.

No schema, table, queue, service, background thread, runtime, provider, platform adapter, or dependency was added.

## Remaining boundaries

- The supported local application is single-supervisor. Revision/state/code CAS also blocks stale database writes, but this evidence does not claim zero orphan side effects for an arbitrary second process that bypasses the supervisor and directly invokes a domain adapter before its CAS fails.
- Real running-task interruption, provider reconciliation, platform acceptance, review, scheduled publication, and public visibility are **NOT RUN**.
- This working tree is not a new release freeze. The earlier `0592b6f` receipt does not cover it.
- Production liquid-glass styling still waits for the user's selection among the three ignored local candidates.
- The next development slice is duplicate-download ownership: wait while the owner is active, reuse its ready asset, and propagate its failed/canceled terminal result precisely.
